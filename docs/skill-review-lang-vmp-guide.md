## 1. 先校准：本指南假设的架构 vs. DartVMP

指南整本围绕一个前提：**产物最终要交给解释器 `eval`/`exec`，攻击者 hook 那一刻就能拿到明文。**
它对这类架构的核心结论是"**VMP 保护的是壳，不是明文，收益很低**"，并反复建议"先把每构建常量
随机化用满再说"。

DartVMP 的模型不同：

| | 指南假设（ShellVMP 式） | DartVMP |
|---|---|---|
| 磁盘上是 | 密文骨架，运行期解密成**脚本** | 密文容器，运行期解密成**私有字节码** |
| 谁来读 | 宿主语言的解释器（bash/python…） | 我们自带的 C 解释器，无 `eval` 环节 |
| 单点 hook | `execve` / `memfd` / 解释器内存 → 直接拿明文脚本 | **不存在**这个点：语义从不以可执行文本形式出现 |
| 明文在哪里出现 | 解释器 fork/exec 前的完整脚本 | 只在 VM 内部栈/arena，以及**跨 FFI 的返回值** |

**推论（重要）**：指南里"筛子①"对 ShellVMP 是个坏消息，对 DartVMP 反而是**好消息**——我们的
"明文窗口"不在"交给解释器 eval"那一步。**对这个架构，VMP 是"保护明文"的手段，不只是"保护壳"。**

**但窗口没有消失，只是换了位置**：我们的窗口是 **FFI 边界**。第 4.1 节展开。

### 术语映射

| 指南术语 | DartVMP 对应物 | 状态 |
|---|---|---|
| L2 载荷加密 | 模块容器（opcode 置换 + 流密码 + tag） | 已有 |
| L3 语义令牌化 | 源码→私有字节码（VM 指令集本身） | 已有 —— **令牌化就是 VMP 的翻译过程本身** |
| L4 运行时对抗 | `DVMP_ANTIDEBUG`（默认开，反应收窄缓存而非拒绝启动） | 部分；C 层加固见 §3.1 |
| L5 执行者保护 | 解释器本体（`dvmp_vm.c`）**未虚拟化，且用 VMPacker 1.3 虚拟化不了** | **已实测：见 §3.1** |
| L1 外层封装 | Flutter 插件 + `libdartvmp.so` | 已有 |

**注意 L3**：指南把"令牌化"当成一个独立的大工程，因为 bash 需要外挂一张 `alias→真名` 表。
DartVMP **不需要**：把源码编译成自定义字节码，就已经把每个语义单元变成了攻击者不认识的编码。
指南里真正还能用的只剩"**别让函数名/常量以明文出现在元数据里**"（见 4.4）。

## 2. 按攻击路径分工（指南最重要的方法论）

指南要求每个组件必须能回答"我堵的是 A/B/C/D 哪条路"。按它的框架评估 DartVMP：

| 路径 | DartVMP 现状 | 评价 |
|---|---|---|
| **A 静态分析** | 受保护函数在 `libapp.so` 里无源码、无机器码；算法常量（`2654435761`/`0xDEADBEEF`/FNV basis）实测**均不在**两个 `.so` 里；`kAlphabet` canary 也不在 | **★★★ 已达标**，`verify_protection.ps1` 在 CI 里守着 |
| **B 动态调试** | Dart VM Service / DevTools 是**主导路径**，C 层无解（明文必须跨 FFI） | **✗ 空** |
| **C 内存 dump** | guarded buffer + 每次调用重封装；但单次 dump 仍可命中调用窗口内的明文 | **★☆ 部分** |
| **D 篡改机制** | 容器 `crc32` + `fnv1a` tag 挡住了改字节；但**解释器本体是明文 C、8 个导出符号，patch 掉校验即可** | **★☆ 部分** |

**覆盖矩阵的空白格是 B 和 D**，与指南的警告一致（"VMP 不防内存 dump"、"共享信任根，无纵深防御"）。
指南同时给出一条我们没利用的观察：**"整体强度 ≈ 最弱组件"**。目前最弱的是 B。

### B 路径为什么在本项目里格外严重

指南说"解释器执行时必须拿到明文，这是物理必需"。对我们，这句话要改写成：

> **受保护函数的返回值必须跨 FFI 交给 Dart 调用方，这是物理必需。**

也就是说：**能留在 VM 内部的中间量是安全的，返回值不是。** 这直接决定了"哪些函数值得保护"
（4.1 节）。

## 3. 指南里**不可复用**的部分（避免白做功）

诚实列出来，免得以后照着做出无效功：

| 机制 | 为什么不用 |
|---|---|
| `PR_SET_DUMPABLE=0` + **seccomp-BPF** | glibc/Linux 专用；Flutter 进程不能自我 seccomp（会杀掉 Flutter engine 自己的 syscall）。指南自己也标注"Android app 域有 seccomp 白名单" |
| `TracerPid` / frida 扫描 / LD_PRELOAD 检测 | C 层对抗，按既定分工归 VMPacker |
| V6 链式动态跳跃块解密（`_s`/`_ck`/`JUMP_DIST=7`） | 解决的是"**文本分块**的执行状态重放"。DartVMP 的字节码本来就没有可读块结构，且"编译期模拟执行"这一门槛对我们不存在（字节码是编译产物，天然确定） |
| 不透明谓词 / 诱饵块 / 垃圾块 | 针对"加密块可被统计分类"。我们的容器是**单一密文 blob**，没有"块"这个可观测单位，注入诱饵只会让 blob 变大 |
| V7 解释器魔改（接管 builtin、令牌表下沉 C 层） | 我们**已经在 C 层**——这正是指南推荐却难做到的形态 |
| "检测到入侵就毒化密钥，不要报警" | 与业务约束冲突：毒化会让 `verifyLicense` 静默返回错误结果，等于破坏业务逻辑。见 4.5 |

**一条被证伪的机制值得记下**：指南实测 `PROT_NONE` **拦不住** `/proc/pid/mem`（内核走
`get_user_pages`，不查用户页表权限）。所以"解密后立即 mprotect 成不可读"这条路不用试了。

### 3.1 L5 执行者保护：工具跑起来了，真机测了，结论是撑不住

VMPacker（github.com/bivex/VMPacker，Go 写的 ARM64 ELF 虚拟化器）通过**符号名**
选函数：`vmpacker -func "a,b,c" -v -o out.so in.so`——这不是猜的，是从它自己的
`test/android/scripts/protect_and_repack.sh` 读出来的，那个脚本正是把 `.so` 从 APK 里解出来
再喂给它，所以**共享库支持是确定的**，也不需要任何源码标注。

**这一轮的进展和上一轮相反：工具已经在本机从源码构建并跑起来了**（`tool/build_vmpacker.ps1`：
用 NDK 的 clang/ld.lld/objcopy 编出 VM 解释器 stub——它 Makefile 里期待的 `aarch64-linux-gnu-`
其实并不需要——再编 Go 的 packer），而且**第一次把受保护的 APK 装到真机上跑**。结果是这一节
最重要的结论：

> **七个被虚拟化的函数里，只有两个能在真机上正确运行；五个让应用在画出第一帧之前 SIGSEGV。
> 能跑的那两个恰恰是最不值钱的（无调用、无全局变量），而真正该藏的 `unpermute_code` 属于跑不
> 起来的那一类。**

逐目标实测（root 的小米 12，Android 13，arm64-v8a）：

| 目标 | 真机 | 原因 |
|---|---|---|
| `keystream_seed` | 正确 | 4 条指令，无调用、无全局变量 |
| `apply_keystream` | 正确 | 79 条指令，全是立即数/寄存器/字节读写/分支 |
| `permute_code` | SIGSEGV `0x0` | 用 `adrp` 读 `kWidth[]` |
| `unpermute_code` | SIGSEGV `0x6dcc` | `bl dvmp_vm_set_error` |
| `dvmp_body_tag` | SIGSEGV `0x6d60` | `bl dvmp_fnv1a64` |
| `dvmp_mask_keystream` | SIGSEGV | 调用 `dvmp_sha256`，且有局部数组 |
| `code_store_build` | SIGSEGV | 调用五个函数 |

出错地址就是诊断：VMPacker 的 VM 只重定位被翻译函数**内部**的分支，外部 `bl` 保留链接时地址，
VM 跳过去时没加加载基址，所以**出错地址等于调用目标**（`0x6d60`/`0x6dcc` 正是 `llvm-objdump -d`
给出的那两个调用目标）。`adrp` 读全局变量是同一类问题。

由此产生的东西里，最有价值的是**一道不需要真机的检查**：`tool/apply_vmpacker.ps1` 现在用
`llvm-objdump` 扫每个目标的指令范围，只要出现 `bl`/`blr`/`adrp`/`adr`/`[pc, …]` 就按名字和偏移
拒绝。它反向验证过（对真实库确实报，例如 `+0x4428 bl 0x9624 <vmp_secure_alloc>`）。本可以省下
一台设备、一份 tombstone 和一轮二分。

两个额外代价，都在源码层面修掉了：**栈金丝雀**（NDK 默认 `-fstack-protector-strong`，VM 不复现
`mrs xN, TPIDR_EL0`，于是金丝雀读访问在 `x19=0` 上崩，`fault addr 0x28` 字面上就是那条指令的
`#0x28`；`DVMP_VMPACKER_TARGET` 因此带 `no_stack_protector`）和 **clang 内联 builtin 产生的 SIMD**
（`-fno-vectorize` 无效，因为那是 `memset`/`memcpy` 的内联展开；用 `no_builtin` + 标量赋值 +
scatter 建表解决）。

能做完、也确实做完了的是交接面和验收，而且每个分支都反向验证过：

| 分支 | 结果 |
|---|---|
| 工具不存在 | `-AllowMissing` 打印 `RESULT: NOT APPLIED` 并退出 0；不加则抛错退出 1 |
| 输入是**已 strip** 的 `.so` | 前置检查拒绝：`has no symbol table, so VMPacker cannot find any function in it` |
| 输入是 **x86_64** 的库 | 拒绝并指明机器类型（构建会保留按 ABI 命名的未 strip 副本，读错 ABI 是个真实的坑） |
| 目标名不存在（被 `-O2` 内联掉） | 前置检查拒绝并指出要用 `-DDVMP_VMPACKER=ON` |
| 目标里有调用或 `adrp` | 拒绝，并报出指令与偏移 |
| 目标的辅助函数留在外面 | 拒绝（`op_tables` 曾经就是这样一个函数体） |
| 只翻译了一部分 | 拒绝：`translated these targets only partially: … 64/70` |
| 工具退出 0 但**什么都没做** | 后置检查拒绝：逐字节比对目标入口地址前后 |
| 工具真的改动了 | `RESULT: APPLIED`，导出 ABI 前后都是 9 个 |
| 库跑不起来 | `tool/verify_device_run.ps1` 装上真机跑，有崩溃记录就失败 |

四条测量出来的结论：

1. **交付物必须留符号表，而且必须按 ABI 命名。** Gradle 会**原地** strip 掉 CMake 产物，
   有时候有符号有时候没有，取决于最后跑的是哪个 task；第一版用了一个通用文件名，结果 x86_64
   那次构建把它覆盖了。现在每个 ABI 一份 `build/unstripped/libdartvmp.unstripped.<abi>.so`。
2. **`noinline` 是承重的，反方向的 `always_inline` 也是。** `-O2` 下小辅助函数没有独立存在；
   而被两个目标调用的 `static` 辅助函数会保留自己的函数体——那正是跳板想藏的东西。
3. **"构建期能找到、运行期调不到"在本工具链上表达不出来。** 实测：非 static 但 hidden 可见性的
   函数（`dvmp_module`、`dvmp_vm_run`）在最终 `.so` 里就是 `t`；加 `visibility("default")` 会变
   `T` 但同时进 `.dynsym`（可被 `dlsym` 调用）；再叠上钉住导出的 version script，`local: *`
   又把它们打回 `t`。二选一，本项目选**不导出**。
4. **带栈金丝雀的目标不是目标**，见上。

**目标选择也是这轮的结论，而且是缩小而不是扩大**：默认只虚拟化真机验证过的两个
（`apply_keystream`、`keystream_seed`），其余五个放在 `#+pcrel` 段里、由上述检查拒绝。
**不碰** `dvmp_vm_run` 和 `dvmp_code_ensure`——受保护函数跑在第二台解释器上，把内层循环虚拟化
等于在系统最热的路径上套一层 VM；而且实测它连翻译都过不去（`1029/1053`，剩下 24 条是 SIMD 寄存器
里的 16 字节结构体拷贝）。

**对 L5 的诚实交代**：这一层没有被解决。C 层虚拟化现在只覆盖两个"藏了也几乎不值钱"的函数，
解释器本身仍然是可读的 AArch64，所以"读 `dvmp_vm.c` 就知道每个 opcode 干什么"这条路径完全没变。
私有指令集映射的保护来自第 7 项（关键化随机置换），不是来自这一层。

## 4. 复核中发现的 5 个可落地项

### 4.1 ★ 明文暴露面分类（最重要的发现）

指南"筛子①"问的是"明文窗口在不在保护面内"。把它套到 DartVMP 的 9 个受保护函数上，得到一个
**可量化的收益指标**：

> **VMP 的收益 = 留在 VM 内部的明文比例 × 该明文的敏感度。**

按"返回值把多少信息交给 Dart 堆"分类：

| 函数 | 返回值 | 跨 FFI 泄露的内容 | 保护的含金量 |
|---|---|---|---|
| `verifyLicense` | `bool` | 1 bit | **高** —— `key`/`groups`/`expected`/`sum` 全程留在 VM |
| `checkSum` | `int`（`% 1048576`，且过了 finaliser 混合） | 20 bit 的混合结果 | **高** —— 输入是 `normalizeKey` 的输出，本就不敏感 |
| `selfTest` | `bool` | 1 bit | **高** |
| `commandChecksum` | `int`（64 位 FNV） | 64 位哈希 | 中 |
| `add` | `int` | 就是答案本身 | 中（逻辑本身无秘密） |
| `base32Index` | `int` | 查表结果，可由 `kAlphabet` 直接复现 | 低 |
| `deviceToken` | `int`（64 位混合值） | **返回的令牌就是最终产物** | **低** —— token 的用途就是交出去，protected 与否几乎无差别 |
| `normalizeKey` | `String` | **规范化后的完整明文** | **低** |
| `makeLicenseKey` | `String` | **生成好的完整密钥** | **低**（实现上它内部调用了 `normalizeKey`+`checkSum`） |

**结论（应当写进文档的第一原则）**：

DartVMP 真正能保护的是"**结果本身不含秘密**"的函数——典型就是
`verifyLicense` 这种"输入 + 输出都无所谓、只有中间过程是秘密"的整函数校验。
对"输出即产物"的函数（`makeLicenseKey`/`normalizeKey`/`deviceToken`），
把函数体搬进 VM **只是让攻击者多花一次调用的力气**：直接调用受保护函数、拿它的返回值就行，
根本不用还原算法。

这与指南 §1"筛子①"是同一个道理，只是"eval 窗口"换成了"FFI 返回值窗口"。

> **对通用 VMP 的含义**：这是**产品定位**问题，不是实现问题。通用 DartVMP 应该明确告诉使用者：
> "适合保护：整函数校验、判定、派生中间量不外泄的逻辑；不适合保护：返回即产物的函数。"
> 这属于"防护范围有边界"的结构性表述，不是缺陷。

### 4.2 ★★ 自己代码里的真实泄露：AOT oracle（已修）

**指南原话**："明文窗口若落在保护面之外，VMP 保护不到那一刻。"
**DartVMP 的对应物**：`app/lib/main.dart` 里的 `_dartDeviceToken`——一份与受保护
`deviceToken` **逐字等价**的明文 Dart 实现，用于性能对比卡片。

实测证据（`app/build/.../stripReleaseDebugSymbols/out/lib/arm64-v8a/libapp.so`，release）：

```
_dartDeviceToken                     PRESENT x1 @ 231528
```

进一步扫描**没有**找到算法常量（`0x9E3779B1`、FNV basis `0xCC1E73F5D3A5B7C1`、
`kAlphabet` 均 ABSENT）——说明 canary 体系是有效的，但 **oracle 的名字进了 AOT snapshot
的名称表**，且那个函数被 `_runBenchmark()` 真实调用。

**为什么这比"算法泄露"更糟**（指南没直说，但逻辑是它的）：

- 算法泄露 → 攻击者要**理解**它（读反汇编、重建语义）
- **oracle 泄露 → 攻击者只需要调用它**。有了逐字节等价的参考实现，还原受保护函数从
  "逆向题"退化成"**逐位比对的是非题**"——成本下降一个量级。

**已修**：

1. `benchmarkBaselineDeviceToken` 只在非 release 构建可达：`_runBenchmark()` 在
   **任何调用点之前**用 `if (kReleaseMode) return` 短路，AOT 编译器据此把整个函数从
   release snapshot 里摇掉。
2. `Vmp.verifyImage()` 同样加 `if (!kReleaseMode)` 门——它会把**整个密文容器复制进 Dart 堆**
   供检查，是诊断手段，不该出现在用户路径上。
3. `tool/verify_protection.ps1` 新增检查 5：release `libapp.so` 里出现
   `benchmarkBaselineDeviceToken` 即构建失败（反向验证：改回去必须 FAIL）。
4. `app/test/vmp_e2e_test.dart` 里那条**把泄露当成规范**的断言
   （`expect(main.contains('_dartDeviceToken'), isTrue)`）改成断言"它被门控住"。

> 原来的测试守的是"这个副本存在且被标注"，方向反了：它锁住了泄露。
> 指南第七节"安全设计自检"里没有这一条，但它的 oracle 相关条目（"篡改与错口令**不可区分**"）
> 是同一个思路。

### 4.3 构建期"保护面存在性断言"

**指南铁律 4**："保护面必须有单一真源 + 存在性断言；**缺项必须是构建失败，不能是静默警告**。"

DartVMP 的风险点很具体：`// @vmp` 标注存在，但若某个函数因为**语言子集不支持**被编译器拒绝，
或者被 `_call` 的索引补丁漏掉，可能表现为"构建成功、保护面少一项"。

现状：`vmpc check` 做产物自检、`verify_protection.ps1` 查泄露，但**没有**"`@vmp` 数量 ==
容器内函数数量"这条断言。**建议补**（未实现，见第 5 节）。

这条对"通用 VMP"尤其重要：使用者加了 `@vmp` 却没生效，是最坏的失败形态。

### 4.4 词法层残留：函数名以明文进容器元数据

`tool/vmpc/lib/src/c_emitter.dart:83`：

```dart
sb.writeln('  { ${ids[i]}u, ${f.arity}u, "${f.name}" },');
```

`kDvmpEntries[]` 把 9 个函数名作为字符串字面量直接放进 `libdartvmp.so`。
`verify_protection.ps1` 已经把它标注为"预期、非算法泄露"——**这个判断是对的**，但它有一个
指南提醒过的后果：

> 指南 §3.5（结构—词法绑定）："**攻击者可以用明文的那一维，反推被保护的那一维。**"

函数名叫 `verifyLicense`/`checkSum`/`normalizeKey`，等于给攻击者一份**保护面地图 + 算法族
提示**（"这里有个校验函数"、"这里有个 512 轮混合"）。而字节码 blob 本身是密文，两者一对比，
最省力的攻击路径就变成了"按名字去猜语义"。

指南给的缓解模板（"密文驻留 + 按需解密"）可以直接套：名字以 per-build 掩码存储，
查找时逐字节解到栈上比较、用完即擦，`Vmp.functions()` 仍能对外提供明文（它是开发接口）。
成本很低，收益是**从产物里移除"哪里值得逆向"的路标**。

（`vmpc.dart disasm` 已经支持 `--seed`，说明"用种子掩码元数据"这个模式在工具链里是现成的。）

### 4.5 反调试的"分离"设计（与业务约束的冲突要显式处理）

**指南**："检测到入侵要**毒化密钥**，不要报警——报警可绕，破坏不可绕。"
**用户硬约束**："不影响业务代码"。

这两条在本项目里**直接冲突**：毒化密钥会让 `verifyLicense` 静默返回错误结果，
那就是"影响业务代码"。

**可行的折中（建议，未实现）**：毒化**只允许污染保护边界内部的状态**，不允许改变对外的
返回值语义。具体说，"被测到调试"时的降级动作应当是：

- ✅ 让**后续会话的密钥演进**变得不可预测（攻击者拿到的 dump 拼不起来）
- ✅ 让反调试分支本身在编译期与业务构建分离（指南"环境门控必须编译期固化"）
- ❌ **不能**让 `verifyLicense(正确key)` 返回 `false`

顺带一条指南的实测结论值得记：**"检测时间这类间接指标必须在 VMP 构建下关闭"**——VM 解释
天然慢 10~100 倍，时间窗检测会把正常调用误判成调试停顿（`rc=113`）。我们的 `DVMP_ANTIDEBUG`
目前**默认关闭**，与这条一致；将来若开启，**不要引入基于时间的判据**。

## 5. 建议清单（按性价比排序）

| # | 项 | 成本 | 收益 | 状态 |
|---|---|---|---|---|
| 1 | release 构建移除 AOT oracle；`verify_protection.ps1` 加检查 | 低 | **高**（堵掉最省力的攻击路径） | **✅ 已实现** |
| 2 | `Vmp.verifyImage()` 移出生产路径 | 低 | 中（不再主动把容器交给调试器） | **✅ 已实现** |
| 3 | 构建期断言：`@vmp` 数量 == 容器函数数量；`protected/` 里不许有无标注函数 | 低 | 中（消灭"静默没保护上"） | **✅ 已实现** |
| 4 | `kDvmpEntries[]` 函数名掩码化 + 按需逐字节解出 | 中 | 中（移除保护面路标） | **✅ 已实现** |
| 5 | 文档写明"适配/不适配的函数类型"（4.1）+ 攻击路径对照表 | 低 | 中（对外承诺诚实且不自贬） | **✅ 已实现** |
| 6 | 每次调用的运行时 nonce / 会话密钥 | 中 | 中 | **✅ 已实现** |
| 7 | 分块惰性解密（单次 dump 拿不到全模块明文） | 高 | **高** | **❌ 尝试后回退** |

### 关于第 7 项：为什么回退

指南指出"**让表从静态数据变成状态相关数据**，直接破坏'多次 dump 累积拼接'的前提"。
对本项目，这条的落地形态就是分块惰性解密 + 会话 nonce。nonce 那一半**已经实现**（第 6 项），
分块那一半没有做成。

三代实现，三种静默的状态 bug，症状**完全相同**：

| 代 | bug | 表象 |
|---|---|---|
| 1 | 一个编解码函数被两个调用方以**相反意图**共用（seal 要密文、fetch 要明文），XOR 是自逆所以后者抹掉前者 | `chunk failed its tag`，报出的字节却明显是明文 |
| 2 | 用**模块级**"是否明文"标志做幂等保护，第一块翻转后其余每块都被跳过 | 同上 |
| 3 | 同一 `code` 指针在取指处是"函数基址"、在操作数读取处被当作"当前指令" | 每个函数的第一条指令正确、之后全部错位；`load` 读出 slot 2850 而不是 0 |

第 3 个根因是靠 `tool/walk_bytecode.py`（独立解码容器并反汇编）定位的——解释器自身的
诊断已经把矛头指向三层无辜的代码。**这个工具留在仓库里**，因为"独立第二实现"是这类
项目唯一可靠的定位手段，这也正是指南第一条心法"一切结论基于实测"的意思。

**回退的理由**：这三代都没有达到"可以发布"的稳定度，而它们要换来的收益（把单次 dump
的窗口从整个指令流收窄到一块）在没有它的前提下**并不影响任何已验证的结论**——会话密钥
那半已经让工作副本不可离线解密。继续在一个会话末尾打补丁，风险高于收益。

**下一步该怎么做**（如果要重做）：把分块状态做成**显式且局部**的东西——每块一个状态字节，
`chunk_set(m, i, plain)` 幂等地设置；`open`/`seal` 循环直接调用它，fetch 用 `live_chunk`
哨兵；并且**先写 walk-style 的对拍测试再写 C**。

### 第 6 项的一个额外发现

实现会话密钥时暴露出 `tool/hostlib/CMakeLists.txt` 的一个**真 bug**：它用 `option(DVMP_HOSTLIB_DIAGNOSTICS)` 控制 `DVMP_NO_DIAGNOSTICS`，但代码里判断的是
`DVMP_DIAGNOSTICS`，而且 `add_subdirectory` 把**核心项目**同名 option 的值写进了 CMake
缓存——所以桌面临时库实际上一直在按缓存值编译，`-DDVMP_HOSTLIB_DIAGNOSTICS=OFF` 从未
生效过。已修（显式 `target_compile_definitions(... DVMP_DIAGNOSTICS=1)` 并在
`build_native.ps1` 里显式传参）。

## 7. 补漏：本轮随后自查出的两个问题

指南"按攻击路径分工"要求每个组件能回答"我堵的是哪条路"。按这个标准回头审自己，
发现两个**组件本身有问题**而不是覆盖有缺口的地方：

### 7.1 反调试层有一个运行期后门（已修）

`dvmp_antidebug.c` 里 `DARTVMP_NO_ANTIDEBUG` 原先只是运行期 `getenv` 判断：

```
DARTVMP_NO_ANTIDEBUG=1 ./app        # 整层反调试失效
```

两个后果：**任何能设环境变量的人都能关掉这一层**，而且变量名可以在出货的 `.so` 里
grep 到。这与指南 L0 那条"**环境门控必须编译期固化**（运行期可改 = 可绕过）"直接冲突，
而我在第 3 节讲不可复用机制时**引用过这条原则却没把它用到自己的代码上**。

修法：把它编译进 `DVMP_DIAGNOSTICS` 门（测试库有、出货库没有），并加
`tool/verify_antidebug_gate.ps1`——它构建两种配置、断言前者二进制里有这个名字、后者没有。
"因为错误原因而通过"的门禁比没有门禁更糟，所以这个检查本身也做了反向验证（去掉
`#if` 后它必须 FAIL）。

### 7.2 篡改检测只在生成器侧被证明（已记录，未修）

README 的攻击路径表把"改字节"标成**强**。实测下来，证明它的是
`image_contract_test.dart`（Dart 侧跑打包器和 tag/CRC 数学）；运行时自己的
`module_open_locked` 校验路径只是**间接**被覆盖——**坏掉**会让全套失败，但**悄悄不再
触发**不会被发现，因为没有任何测试会给运行时喂一个损坏的容器。

真正的补法是一个接受任意容器、报告拒绝原因的诊断入口（`dartvmp_load_image_probe`）。
它本身有风险：在出货库里放一个"加载任意镜像"的入口是新的攻击面，所以必须只存在于
`DVMP_DIAGNOSTICS` 构建里——也就是和上面那条同一把锁。**已写进两份 README 的局限里，
未实现。**

这两条的共同教训：**"我引用过的原则"和"我代码里做到的事"是两件事，得分开核对。**

## 8. 独立对抗性审计（同轮后续）

本节完成后又跑了一次**独立审计**：它从零重建了容器格式（Python 重实现 packer/emitter）、
构造任意镜像编译进真实运行时、对活动 Dart 进程做跨进程内存 dump、并用 4 isolate 探针
跑并发。结果如下——**值得记下来的是失效模式，不是单个 bug**：

| 级别 | 发现 | 状态 |
|---|---|---|
| 严重 | **body 从未被擦除**：seal 只擦副本，`m->body` 把解码后的整个模块留了整个进程生命周期。审计在**全套测试通过之后**的单个内存页里读出了受保护字母表字符串和 `add` 的解码字节码 | **已修** + 反向验证的回归测试 |
| 高 | **文档宣称的 native lock 根本不存在**：并发调用返回错答案、报 module corrupt、最后访问违例崩进程 | **已修**（进程级锁）+ C harness 验证 |
| 高 | `need_builder` 只查 tag 不查 kind，构造镜像可让 `strBuild` 把字符串当 builder 读 → 野指针 | **已修**（builder 独立 slot tag） |
| 高 | `entry_name_eq` 的界检查在**读之后**，query 短于名字时会读过 NUL | **已修** |
| 中 | 诊断版运行时被部署进 Windows **Release** runner 目录（导出 `code_probe`/`session_probe`） | **已修** |
| 中 | app 的 stub 仍把 7/9 个受保护函数名以明文带进 `libapp.so`（掩码表只保护了运行时那一侧） | **未修**，已写入文档 |
| 中 | `strParseInt` 溢出返回截断前缀，与 oracle 的 clamp 不一致 | **已修** |
| 中 | 生成的 `.inc` 不是构建依赖 → 重新生成不触发重编 → 出货过期镜像 | **已修** |
| 中 | `vmpc check` 的"本体泄漏"门槛可绕过（`for(` 无空格、路径含 `generated`） | **未修**，已记录 |
| 低 | 错误通道会把模块内的字符串带给 Dart（`bytecode abort: <literal>`） | **未修**，已记录 |
| 低 | `Vmp.markedProbes` 是幻影字符串（仓库里根本不存在），使 `verifyImage()` 的泄漏证据恒为空 | **未修**，已记录 |

### 最值得记住的一条

**每一条"严重/高"都是同一句话：文档描述的是**设计意图**，代码实现的是**别的东西**。**
文字对计划的描述没错，对**当前状态**的描述错了。所以修复都配了会在行为回退时失败的检查，
而不是改注释——改好的注释同样"正确"，也同样没被验证。

这也是为什么本轮新增的每个修复都做了**反向验证**：去掉锁 → harness 报出 3148 个错误；
去掉 body 擦除 → 残留探针立刻失败；去掉 `#if` 门 → 反调试门禁 FAIL；篡改 manifest →
build-id 检查 FAIL。**没有反向验证的"已修复"只是又一次断言。**

## 6. 一句话总结

> 指南的方法论（**按攻击路径分工 + 结构—词法绑定 + 明文窗口判据 + 存在性断言 + fail-closed**）
> 对 DartVMP **全部适用**；
> 它的**具体机制**（seccomp / 令牌表 / 链式块解密 / 毒化密钥）**大部分不适用**，
> 因为 DartVMP 已经站在指南推荐却难到达的位置（C 层单进程、无语义文本）。
>
> **本轮最大的收获不是新增一层保护，而是发现"我们的明文窗口不在磁盘上，而在返回值里"**——
> 并据此清掉了一个比算法泄露更严重的 oracle。
