# Publishing FDartVMP: the git flow

Short version, for this project specifically. The long version is the git book.

## Where this repository stands

There was **no version control history here at all**. The directory sits inside another
repository (`D:/ai`), but that one has no commits either, and everything under `DS-H/` is
untracked in it. So there is nothing to preserve and nothing to inherit: the first commit is
the beginning of the project's history.

That is why the flow below starts with `git init`. It has already been done once for the
packaged snapshot — if you are working from that, skip to "Pushing it".

## One-time setup

```bash
# from the project root
git init -b main

# identify yourself (only needed once per machine)
git config user.name  "haothtrteen"
git config user.email "2557976190@qq.com"

# check what would go in, before adding anything
git status --short
```

Two files at the root are deliberately **not** committed and are listed in `.gitignore`:
`构建.md` (a saved copy of a chat reply, not project documentation) and any `*.obj` /
`*.exe` a local build leaves behind. Delete those ignore lines if you want them in.

## The commit

```bash
git add -A
git status --short          # eyeball the list: 130-odd files, no build/ output
git commit -m "FDartVMP: source-level VM protection for Flutter, with the CTF target"
```

What is in the commit and what is not:

| Committed | Ignored, and why |
|---|---|
| `README.md`, `README.zh-CN.md`, `docs/`, `LICENSE`, `LICENSING.md`, `CHANGELOG.md`, `SECURITY.md`, `CONTRIBUTING.md` | `build/` — every build product, including the challenge APK and the released `.so` |
| `packages/dartvmp/` (runtime sources), `tool/` (compiler and every check), `protected/` (protected sources), `app/lib/`, `app/test/`, `app/android/`, `app/windows/` | `packages/dartvmp/generated/`, `app/lib/generated/`, `app/test/generated/` — generated by `dart run tool/build.dart`, and the container's seed is random per build |
| `.gitignore`, `.gitattributes` | `.dart_tool/` — pub caches; thousands of files |
| `app/pubspec.lock`, `tool/vmpc/pubspec.lock` | `app/dartvmp.dll` — the test runtime, deployed by `tool/build_native.ps1` |

`git status --porcelain` must be **empty** after the commit. If it is not, the ignore list
is missing something and the repository will look dirty to everyone who clones it.

## Pushing it

Create an **empty** repository on GitHub (no README, no license file — this project already
has both, and GitHub's "add a license" button would create a second, conflicting one):

```bash
git remote add origin git@github.com:<you>/FDartVMP.git
git push -u origin main
```

Then, on the repository page:

- GitHub will detect `LICENSE` and label the project **AGPL-3.0**. Make sure the licence
  shown is the one you intend, because for a dual-licensed project the *public* label is
  AGPL while commercial terms live in `LICENSING.md`.
- Put the challenge target in a **Release**, not in the repository: a 15 MB binary commit
  cannot be removed from history without rewriting it, and the repository is meant to be
  the engine rather than the payload. Attach the APK and paste its SHA-256 in the release
  notes (the checklist in `docs/CHALLENGE.md` says where to get it).

## The rules that matter later

- **Never commit the released challenge APK.** Its flag differs from the reference one in
  `protected/challenge.dart`, and the post tells solvers the repository's copy is not the
  target. Publishing both together would end the challenge.
- **Never force-push `main` once it is public.** Contributors' clones break, and the AGPL
  notice you are relying on lives in that history.
- **A contribution needs the CLA before it can be merged** — not a formality: without the
  right to relicense contributed code, a single merged pull request makes the commercial
  half of the dual licence unsellable. `CONTRIBUTING.md` states this.
- **Do not commit generated artifacts**, even though they are convenient. The container is
  rebuilt with a fresh random seed by design; committing one makes the diff noisy and hides
  the fact that a build step is required.

## Working on it day to day

```bash
git switch -c fix/<something>      # branch
# ... change, then run the gate before committing ...
powershell -ExecutionPolicy Bypass -File tool/test.ps1 -Release
git add -p                          # stage in hunks, read what you staged
git commit -m "..."
git push -u origin fix/<something>  # then open a pull request
```

The gate is not optional in this project: `tool/test.ps1 -Release` includes the protection
scan (zero protected names and zero mechanism phrases in the shipped snapshot), the
cryptographic vectors, the runtime-versus-manifest policy comparison, the device run, and
`tool/check_encoding.py` (every text file must be valid UTF-8 — a PowerShell
`Get-Content`/`Set-Content` round trip on a CP936 console silently corrupts non-ASCII, which
is how this repository's README was once damaged).
