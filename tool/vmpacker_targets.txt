# C-layer virtualization targets for VMPacker.
#
# One function name per line. `#` starts a comment; blank lines are ignored.
# `#+name` opens a section selected by the matching switch (`-PcRel`). Everything not
# marked `!` must exist as a symbol in the unstripped libdartvmp.so -
# tool/apply_vmpacker.ps1 refuses to run if any name is missing, because a target that
# has been inlined away or renamed is virtualized silently into nothing.
#
# A name prefixed `!` is the opposite: a helper that must NOT exist as its own
# function, because a virtualized target calls it and an out-of-line copy is a
# plain-AArch64 version of what the trampoline is hiding. See the helper check in
# apply_vmpacker.ps1, which fired for real on the first keyed-permutation build.
#
# THE LIST IS WHAT A DEVICE ALLOWS, NOT A PREFERENCE
# -------------------------------------------------
# Seven functions were virtualized, applied cleanly and passed every structural check.
# Then the protected APK was installed on a real device (rooted Xiaomi 12, Android 13,
# arm64-v8a) and five of the seven killed it. Per target, tested one at a time:
#
#   target                on device        why
#   --------------------  ---------------  ------------------------------------------
#   keystream_seed        runs correctly   no calls, no globals - 4 instructions
#   apply_keystream       runs correctly   79 instructions: immediates, register ops,
#                                          byte loads/stores and branches only
#   permute_code          runs correctly   used to die at address 0 on the kWidth[]
#                                          table's adrp; the table is now op_width(),
#                                          an immediate comparison chain. 93
#                                          instructions, 0 adrp, 0 bl, 0 SIMD, and it
#                                          also had to lose its CSEL (see below).
#   unpermute_code        runs correctly   used to SIGSEGV at 0x6dcc, the address of
#                                          `bl dvmp_vm_set_error`; the message is
#                                          formatted by the caller now. 231
#                                          instructions, 0 adrp, 0 bl, 0 SIMD, no CSEL.
#   dvmp_body_tag         runs correctly   used to SIGSEGV at 0x6d60, the address of
#                                          `bl dvmp_fnv1a64`; the hash is inlined now.
#                                          45 instructions, 0 adrp, 0 bl, 0 SIMD.
#   dvmp_mask_keystream   SIGSEGV          calls dvmp_sha256, and has a local array
#   code_store_build      SIGSEGV          calls five functions
#
# "runs correctly" means the values, not the absence of a crash: the protected APK was
# launched, screenshotted, and every figure on the demo card checked against the Dart
# oracle - add(20,22)=42, makeLicenseKey("demo-seed",7)=ZVEXKFVVCDH93W6R,
# verifyLicense true for the good key and false for the altered one,
# deviceToken("pixel-7",1700000000)=-5031510683369134119, selfTest()=true. Those calls
# are dispatched through the trampolines, and the module cannot open at all unless
# `dvmp_body_tag`, `permute_code` and `unpermute_code` all compute what the Dart
# assembler computed. (build/screen_all5.png; the suite's device step only proves "no
# crash record", which is why this was checked by eye as well.)
#
# VMPacker 1.3's VM remaps branches *inside* the function it translated and nothing
# else, so an external `bl` keeps its link-time address and the VM jumps there without
# adding the library's load bias - which is why the fault address *equals* the call
# target (0x6d60 and 0x6dcc are the two call targets above, from `llvm-objdump -d`).
# `adrp`/`adr`/pc-relative loads are the same story for globals.
#
# FIVE CHANGES, AND THE LAST ONE WAS NOT PREDICTABLE FROM THE OTHER FOUR
# ---------------------------------------------------------------------
#   * `op_width()` in dvmp_module.c - the width table was the only .rodata operand in
#     `permute_code`, and `adrp` is what VMPacker cannot translate.
#   * the error strings and the `dvmp_vm_set_error` call moved out of `unpermute_code`
#     into its caller, which is not a target.
#   * `dvmp_fnv1a64_core` inlined into `dvmp_body_tag` (one definition, two views).
#   * -mgeneral-regs-only on the two cold translation units, via
#     DVMP_VMPACKER_NO_VECTORIZE. This is the change that made the SplitMix64 constants
#     come out as `movz`/`movk` instead of `ldr q` from a constant pool, and it is why
#     `permute_code` went from "Translated: 94/118" to a full translation.
#   * **the CSEL**, and this one is the interesting one because the other four are
#     structural and this is a wrong answer. With all of the above done, VMPacker
#     reported a full translation of all five targets, the APK installed, the process
#     stayed up - and every protected call failed with
#
#         VmpFault(add): the native runtime is not initialised
#                        [opcode 0x20 out of range at +0]
#
#     i.e. the decode walk rejected the very first byte of the instruction stream. A
#     device bisect (tool/bisect_vmpacker.ps1) put it on `unpermute_code`: adding it to
#     the three working targets reproduced the fault, and everything else was fine.
#     Comparing the disassembly against the targets that do work pointed at `CSEL` -
#     present twice in `unpermute_code` (the shuffle's `r % (256 - i)`, and the
#     `i < DVMP_OP_MAX ? i : DVMP_OP_MAX` select in the inverse-table scatter) and
#     absent from `apply_keystream`, `keystream_seed` and `dvmp_body_tag`.
#
#     VMPacker 1.3's VM has a `CSEL` handler (translator.go routes CSEL/CSINC/CSINV/
#     CSNEG to trStackCSEL), so the instruction is "supported"; it computes the wrong
#     answer for at least this shape. The fix is in our source, not in the tool: the
#     shuffle uses an exact identity instead of a remainder
#     (`r - ((r + i) >> 8) * (256 - i)`, valid because i < 38 and r <= 255 so the
#     quotient is exactly the shift), and the inverse table is built by two
#     unconditional scatters instead of one conditional one. `permute_code` and
#     `unpermute_code` now contain no CSEL/CSET/CSINC/CSINV/CSNEG at all, and the
#     device computes every value correctly.
#
#     Not fixed in VMPacker on purpose: the release we build against has to stay the
#     unmodified tool, or the pipeline stops being reproducible from the published
#     archive. Worth reporting upstream - a minimal reproducer would be a function whose
#     only conditional is a `CSEL` over `XZR` and a register, which is the shape
#     `r >= d ? r - d : r` produces.
#
# The `#+pcrel` section keeps the two that still cannot run listed rather than deleted,
# because they are real protection wins the moment the tool can execute them - the mask
# derivation, the store builder - and because the instruction-coverage check in
# apply_vmpacker.ps1 refuses them with the offending instruction named. Selecting that
# section is *expected to fail today*; that failure is the check doing its job.
#
# FOUR more things this cost, all now checked rather than remembered:
#   * the stack canary. The NDK compiles with -fstack-protector-strong, so any target
#     with a local array begins with `mrs x19, TPIDR_EL0` / `ldr x8, [x19, #0x28]`, and
#     VMPacker's VM does not reproduce the TLS read: x19 arrives as zero and the
#     process dies with "fault addr 0x28" - literally the `#0x28` in that instruction.
#     DVMP_VMPACKER_TARGET carries no_stack_protector for this reason.
#   * SIMD. A 256-byte constant fill becomes `movi` + eight `stp q0,q0`, and an inlined
#     memcpy becomes `ldr q`/`str q`; VMPacker 1.3 has no SIMD translation and refuses
#     the whole function (that is what `DVMP_NO_BUILTIN` and the scalar SHA-256 state
#     initialisation in dvmp_sha256.c are for). -fno-vectorize does *not* remove these;
#     -mgeneral-regs-only does.
#   * the opcode set is now shared by a check instead of by memory: adding an opcode to
#     dvmp_wire.h without adding it to the Dart assembler's `kOperandBytes` (or the
#     reverse) fails tool/verify_wire_widths.py, which compares the two through the
#     runtime's own `op_width()` rather than through a second copy of the table.
#   * **compiler clones of a target**. Giving `unpermute_code` two out-parameters, one
#     call site passing NULL and one passing pointers, made clang constant-propagate the
#     NULL checks away and emit `unpermute_code.specialized.1` - the whole shuffle and
#     walk, in plain AArch64, next to a trampoline that had translated "231/231". Same
#     failure as `!op_tables` by a different road. apply_vmpacker.ps1 now refuses any
#     `<target>.something` symbol, and the check was reverse-verified against the
#     artifact that had the clone in it.
#
# The checks around the invocation - target present, helper inlined away, no suffixed
# clones, instruction coverage - are what make this list trustworthy. Each was written
# after watching the failure it catches, and the coverage check fires on every entry in
# the section below.

# Cold, self-contained, and verified on a device running the protected APK: every value
# on the demo card matches the oracle. Adding a name here means adding a line to the
# table above, and the table is only allowed to say "runs correctly" after a screenshot.
apply_keystream
keystream_seed
dvmp_body_tag
permute_code
unpermute_code

# Helpers that must have been inlined into the targets above (or into other functions).
# `op_tables` is the keyed permutation's construction: while it had a body of its own,
# the trampolines hid nothing, because an attacker could call it directly.
!op_tables
!sm_next
!sm_init

#+pcrel
# Translatable, not executable by VMPacker's VM. Both crash the application on a
# device, and each is a target the project wants back as soon as the tool can handle a
# call or an `adrp`:
#   dvmp_mask_keystream  calls dvmp_sha256 (and SHA-256 is far past the size ceiling
#                        as one function)
#   code_store_build     calls five functions and reads globals
dvmp_mask_keystream
code_store_build
